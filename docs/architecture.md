# 技術仕様書 (Architecture Design Document)

## テクノロジースタック

### 言語・ランタイム

| 技術 | バージョン |
|------|-----------|
| Flutter | stable チャンネル(3.x 系) |
| Dart | 3.x(Flutter に同梱) |
| Node.js | v24.x(**アプリではなくハーネス専用**。husky / lint-staged / secretlint) |

> **Node.js が残っている理由**: ガードレール(保護ブランチ検査の起動経路・機密検出)と
> Claude Code / Codex CLI / MCP のインストール経路がすべて npm。
> アプリのビルドには一切関与しない。詳細は `.steering/20260912-kickoff-flutter-setup/design.md`。

### フレームワーク・ライブラリ

| 技術 | バージョン方針 | 用途 | 選定理由 |
|------|-----------|------|----------|
| Material 3 | Flutter 同梱 | UI コンポーネント | 追加依存ゼロ。タッチターゲットとコントラストの既定値が出発点として妥当(**WCAG AA の充足は保証されない**。56dp と主要テキストのコントラストは個別に指定・検証する) |
| Drift | ^2.x | ローカル DB(SQLite) | クエリがコンパイル時に型検査される。マイグレーションの仕組みが標準で付く |
| sqlite3 | ^3.x | SQLite 本体のバンドル | Drift が各 OS で同一バージョンの SQLite を使うために要る。旧 sqlite3_flutter_libs は提供終了(0.6.0+eol)で、本体側のネイティブビルドフックに統合された |
| path_provider | ^2.x | DB ファイルの配置先解決 | OS ごとのドキュメント領域を取得する標準手段 |
| Riverpod (`flutter_riverpod`) | ^3.x | 状態管理・依存注入 | テスト時に `Clock` と `ItemRepository` を差し替えられる |
| uuid | ^4.x | 項目 ID の採番 | 将来のクラウド同期(P2)で衝突しない ID が要る |
| intl | **Flutter SDK が要求する版に合わせる** | 日付の日本語整形 | `2026年9月12日` 形式をロケール経由で出す |

> **`intl` を使わず自前で整形しない理由**: MVP は日本語のみだが、`DateFormat` を通しておけば
> 多言語対応が文字列リソースの追加だけで済む。自前整形は後で必ず書き直しになる。

### 開発ツール

| 技術 | 用途 | 選定理由 |
|------|------|----------|
| `flutter analyze` | lint + 型チェック | Dart は両者を分離できない。`--fatal-infos` で情報レベルも落とす |
| `dart format` | フォーマット | Dart 公式。設定項目がなく議論が起きない |
| `flutter test` | ユニット / ウィジェットテスト | 標準。追加依存なし |
| `build_runner` + `drift_dev` | Drift のコード生成 | スキーマから型安全なクエリを生成する |
| `secretlint` | 機密の混入検出 | Dart エコシステムに同等品がない。pre-commit と CI の 2 層で回す |
| `husky` + `lint-staged` | pre-commit の起動 | 保護ブランチ検査(ベンダー非依存の防衛線)の実体 |

### 生成コードの扱い

**`*.g.dart` / `*.drift.dart` は git で追跡する。**

| 選択肢 | 採否 | 理由 |
| --- | --- | --- |
| 生成物をコミットする | **採用** | CI で `build_runner` を回さずに済む。スキーマ変更の影響が PR の差分で見える |
| `.gitignore` して CI で生成 | 不採用 | CI 時間が伸び、ローカルと CI で生成器のバージョンがずれたときに検知が遅れる |

## アーキテクチャパターン

### レイヤードアーキテクチャ

```
┌──────────────────────────────────────┐
│  UI レイヤー (lib/ui/)                │ ← 画面・ウィジェット
├──────────────────────────────────────┤
│  状態管理レイヤー (lib/state/)         │ ← Notifier・表示モデル変換
├──────────────────────────────────────┤
│  ドメインレイヤー (lib/domain/)        │ ← Item・経過日数の算出・Clock
├──────────────────────────────────────┤
│  データレイヤー (lib/data/)            │ ← Repository・Drift
└──────────────────────────────────────┘
```

#### UI レイヤー

- **責務**: 描画、タップの受付、画面遷移
- **許可**: 状態管理レイヤーの Notifier / Provider を読む
- **禁止**: `ItemRepository` と Drift の型への直接アクセス、`DateTime.now()` の呼び出し、
  経過日数の計算

#### 状態管理レイヤー

- **責務**: ドメインモデルを表示モデル(`ItemView`)へ変換、入力バリデーション、
  取り消し用の一時状態、非同期の成否をUIへ伝える
- **許可**: ドメインレイヤーとデータレイヤーの呼び出し
- **禁止**: `Widget` / `BuildContext` への依存(テストを Flutter 非依存に保つため)

#### ドメインレイヤー

- **責務**: `Item` モデル、`elapsedDays`、`ElapsedLabel`、`Clock` の抽象
- **許可**: 何にも依存しない(Dart の標準ライブラリのみ)
- **禁止**: Drift・Flutter・Riverpod への依存

> **ドメインを純 Dart に保つことが、このアーキテクチャの要。** 経過日数の算出は
> 本プロダクトの中心ロジックで、境界条件(日またぎ・うるう年・夏時間)のテストが要る。
> Flutter に依存しなければ、テストは数ミリ秒で回る。

#### データレイヤー

- **責務**: 永続化、Drift 行 ↔ ドメインモデルの変換、マイグレーション定義
- **許可**: Drift・SQLite へのアクセス
- **禁止**: 経過日数の計算、表示用の文字列整形、`Clock` への依存
  (記録時刻は呼び出し元から引数で受け取る)

### 依存の向き

上から下への一方向のみ。**ドメインレイヤーは誰にも依存しない。**
`ItemRepository` はドメイン側にインターフェースを置き、実装をデータレイヤーに置く
(依存性逆転)。これにより、状態管理レイヤーのテストで Drift を起動せずに済む。

## データ永続化戦略

### ストレージ方式

| データ種別 | ストレージ | フォーマット | 理由 |
|-----------|----------|-------------|------|
| 管理項目(`items`) | SQLite | Drift 管理のテーブル | 構造化データで、P1 の履歴テーブルとリレーションを張る前提 |
| ユーザー設定 | **MVP では持たない** | — | 設定項目が存在しない。P1 の通知設定で初めて必要になる |

**DB ファイル**: `<アプリのドキュメント領域>/lastwhen.sqlite`(`path_provider` で解決)

**日時の保存形式**: UTC のエポックミリ秒(整数)。
タイムゾーンの解釈は表示時のみ。文字列で保存しない(比較とソートが遅く、曖昧さが残る)。

### マイグレーション戦略

Drift の `schemaVersion` と `MigrationStrategy` を使う。

| 原則 | 内容 |
| --- | --- |
| 前進のみ | ダウングレードは実装しない。ストア配信でバージョンが戻ることはない |
| 破壊的変更を避ける | 列の削除・リネームではなく、追加と非使用化で進める |
| 失敗時はデータを保持 | マイグレーション失敗時にテーブルを作り直さない。起動を中断してエラーを出す |
| 検証 | スキーマ変更を含む PR では、旧バージョンの DB からの移行テストを書く |

**`lib/data/database/` と `lib/data/migrations/` は Codex への委託禁止領域**
(`AGENTS.md` §4)。マイグレーションは一度出荷すると修正できず、事故のコストがユーザーの
記録の全損になるため。

### バックアップ戦略

MVP はアプリ独自のバックアップを持たない。OS の自動バックアップに委ねる。

| プラットフォーム | 仕組み | 設定 |
| --- | --- | --- |
| iOS | iCloud バックアップ | DB ファイルを除外指定**しない**(既定で含まれる) |
| Android | Auto Backup for Apps | `allowBackup` を無効化**しない**(既定で有効) |

**復元方法**: 機種変更時に OS のバックアップから復元する。アプリ側の操作は不要。

> **MVP に手動エクスポート(F26)が無い以上、これが唯一の移行手段。**
> バックアップ対象から除外する設定を入れないことが、実質的な要件になる。

## パフォーマンス要件

### レスポンスタイム

| 操作 | 目標時間 | 測定環境 |
|------|---------|---------|
| コールドスタート → 一覧表示 | 1.5 秒以内 | ミドルレンジ Android(RAM 4GB 相当)、項目 20 件 |
| 「やった」タップ → 画面反映 | 100ms 以内 | 同上 |
| 一覧の初回描画(100 件) | 300ms 以内 | 同上 |
| 項目の追加 → 一覧反映 | 200ms 以内 | 同上 |

### リソース使用量

| リソース | 上限 | 理由 |
|---------|------|------|
| メモリ | 150MB 以内(一覧表示時) | ローエンド端末でバックグラウンド強制終了されにくい水準 |
| ディスク(DB) | 1MB 以内(項目 1,000 件) | 1 行あたり数百バイト。MVP の想定規模では問題にならない |
| アプリサイズ | 30MB 以内(Android App Bundle) | ダウンロード離脱を抑える。依存を増やさない方針の裏付け |

## セキュリティアーキテクチャ

### データ保護

- **暗号化**: アプリ独自の暗号化は行わない。OS のファイルレベル暗号化(iOS Data Protection /
  Android File-Based Encryption)に委ねる。保存するのは生活行動の名称と日付のみで、
  認証情報・個人識別情報を含まない
- **アクセス制御**: DB はアプリのサンドボックス内に置く。外部ストレージへ書かない
- **機密情報管理**: アプリに API キー・トークンの類を含めない(外部通信がないため不要)。
  署名鍵は `.gitignore` で追跡対象外(`android/key.properties`・`*.jks`・`*.p12`)

### 入力検証

- **バリデーション**: 項目名はトリム後 1〜50 文字。状態管理レイヤーで検証し、
  データレイヤーにも NOT NULL 制約を置く(二重化)
- **サニタイゼーション**: SQL は Drift のクエリビルダ経由のみ。文字列連結で SQL を組まない
- **エラーハンドリング**: ユーザー向けメッセージに内部例外の文言・スタックトレースを出さない

### 供給網(サプライチェーン)

- 依存は**上記の表に挙げたものに限定する**(`build_runner` / `drift_dev` / `flutter_lints` の
  dev 依存を含む)。**追加には設計上の理由を `design.md` に書く**。
  件数は書かない —— 増減のたびに複数箇所を直す羽目になる
- Dependabot が `pub` / `npm` / `github-actions` / `devcontainers` を monthly で追従する。
  セキュリティ更新は interval と無関係に即時 PR が出る
- Flutter SDK は公式リポジトリの stable ブランチから取得する(`post_create.sh`)。
  コミュニティ製の devcontainer feature には依存しない

## スケーラビリティ設計

### データ増加への対応

- **想定データ量**: 通常利用で 5〜30 件。非機能要件の上限として 100 件、
  設計上の余裕として 1,000 件まで劣化しないこと
- **パフォーマンス劣化対策**: 一覧は `ListView.builder` で遅延生成。
  並び替え(P1)を入れる際は `sort_order` と `last_done_at` にインデックスを張る
- **アーカイブ戦略**: MVP では不要。P1 の履歴(F12)で行数が増えたら、
  項目あたりの保持件数に上限を設けるか、古いログを間引く方針を再検討する

### 機能拡張性

| 拡張 | 想定される変更 |
| --- | --- |
| P1 目安期間 / 状態表示 | `items` に `interval_days` 列を追加。ドメインに状態判定の純関数を足す |
| P1 通知 | 新レイヤー(通知スケジューラ)を追加。通知権限の要求が初めて発生する |
| P1 履歴 | `done_logs` テーブルを追加。`items.last_done_at` は最新ログのキャッシュに役割変更 |
| P1 並び替え | 状態管理レイヤーで並べ替える。データ層のクエリは変えない |
| P1 アイコン | `items` に `icon` 列を追加(v3)。UI 層に対応表を置き、ドメインは保存キーだけを持つ |
| P2 クラウド同期 | リポジトリ層の背後に同期実装を差し込む。`id` が UUID なので衝突しない |

**UI レイヤーを触らずに済む拡張が多いこと**が、このレイヤー分割の狙い。

## テスト戦略

### ユニットテスト

- **フレームワーク**: `flutter_test`(`test` パッケージ互換)
- **対象**: ドメインレイヤー全体(`elapsedDays`・`ElapsedLabel`・バリデーション)、
  状態管理レイヤー(リポジトリをフェイクに差し替える)
- **カバレッジの目安**: ドメインレイヤー 100%、状態管理レイヤー 80% 以上。
  UI レイヤーには数値を置かない(ウィジェットテストで主要導線を押さえる)。
  **CI では計測しない** —— `quality` ジョブは `flutter test` のみで、閾値検査を持たない。
  数値は設計の目安であり、合否はレビューが判定する(`development-guidelines.md`)

### レイヤー依存の検査

`test/architecture/layer_dependency_test.dart` が `lib/` のソースを読み、禁止された import
(`domain` → Flutter / Drift / Riverpod、`ui` → `data`)が無いことを確認する。

> **`analysis_options.yaml` では機械化できない。** `flutter_lints` と標準 analyzer に
> ディレクトリ間 import を禁止する lint は無く、実現には `custom_lint` 等の追加依存が要る。
> 「依存を増やさない」方針と衝突するため、**検査を通常のテストとして書く**。
> `flutter test` で回るので CI の `quality` ジョブがそのまま最終ゲートになる。

### 統合テスト

- **方法**: Drift のインメモリ DB(`NativeDatabase.memory()`)に対してリポジトリ層を回す
- **対象**: CRUD の一巡、記録と取り消し、100 件投入時の一覧取得、
  スキーマ変更時の旧バージョンからの移行

### ウィジェットテスト

- **ツール**: `flutter_test` の `WidgetTester`
- **シナリオ**: 一覧の空状態、「やった」タップで確認が出ないこと、取り消し導線、
  削除の確認ダイアログ、フォントサイズ 200% でのレイアウト

### E2E テスト

**MVP では実装しない。** 画面が 3 つでウィジェットテストが主要導線を覆えるため、
`integration_test` の維持コストが見合わない。P1 で通知(端末機能との連携)が入る段階で再検討する。

## 技術的制約

### 環境要件

| 項目 | 要件 |
| --- | --- |
| 対応 OS | iOS 15 以上 / Android 8.0(API 26)以上 |
| 開発環境 | devcontainer(Debian bookworm + Flutter stable + Node 24 + JDK 17) |
| iOS ビルド | **macOS が必要**。devcontainer では Android ビルドとテストのみ可能 |
| 画面 | スマートフォン縦持ち。タブレット・横向きは MVP で最適化しない |

> **devcontainer で iOS ビルドはできない。** Linux コンテナに Xcode を置けないため。
> MVP の開発とテストは Android とユニット / ウィジェットテストで進め、
> iOS のビルドと実機確認は macOS 上で別途行う。**これはリリース計画上の制約**として、
> ストア申請の準備段階までに手段を確保する必要がある。

### パフォーマンス制約

- 起動時に DB マイグレーションが走る可能性があるため、起動時間の目標は
  マイグレーションなしのケースを指す
- 楽観的 UI 更新を採らない方針のため、書き込み応答が 100ms 要件の下限を決める。
  ローカル SQLite の単行 UPDATE は数ミリ秒で、余裕がある

### セキュリティ制約

- アプリ独自の暗号化を行わないため、端末のロック解除後はデータが平文で読める。
  保存内容の機微度が低いことを前提とした判断で、**機微な内容を扱う機能を将来追加する場合は再評価する**
- OS の自動バックアップに含めるため、クラウド上にデータのコピーが存在する。
  **PRD の「外部サーバーへ送信しない」は「アプリが能動的に送信しない」の意**で、
  OS 標準バックアップ経由のコピーは機種変更時の唯一の移行手段として意図的に許容している。
  プライバシーポリシーとストアのデータ収集申告に明記する

## 依存関係管理

| ライブラリ | 用途 | バージョン管理方針 |
|-----------|------|-------------------|
| `drift` / `drift_dev` | ローカル DB とコード生成 | キャレット(`^`)。**両者のバージョンを揃える** |
| `sqlite3` | SQLite 本体 | キャレット |
| `path_provider` | ファイル配置先 | キャレット |
| `flutter_riverpod` | 状態管理 | キャレット |
| `uuid` | ID 採番 | キャレット |
| `intl` | 日付整形 | **バージョンを docs に固定で書かない。** `flutter pub get` の解決に従う(Flutter SDK が `flutter_localizations` 経由で版を pin するため、キャレットで指定すると SDK 更新のたびに衝突する) |
| `build_runner` | コード生成の実行 | キャレット(dev 依存) |
| `flutter_lints` | lint ルール | キャレット(dev 依存) |

**`pubspec.lock` は追跡する。** アプリケーション(ライブラリではない)なので、
ローカル・CI・リリースビルドで同じ依存解決を再現する必要がある。
