# プロダクト要求定義書 (Product Requirements Document)

## プロダクト概要

### 名称

**最後にいつ**(LastWhen) - 「最後にやったのはいつ?」を1タップで記録・確認する生活管理アプリ

### プロダクトコンセプト

- **記録ではなく想起**: 予定を立てさせない。「前回いつやったか」を思い出す道具に徹する
- **1タップ**: 記録操作は「やった」ボタン 1 回で完結する。日付入力も確認ダイアログも挟まない
- **経過日数が主役**: 画面で最も大きいのは日付ではなく「何日前」。人が判断に使うのはこちらだから

### プロダクトビジョン

美容院、歯医者、エアコン掃除、歯ブラシ交換、布団干し —— 毎日ではないが定期的に行う生活行動は、
やった記憶はあっても「いつだったか」が抜け落ちる。カレンダーやメモに残しても、後から探す手間が
継続を妨げる。

既存の ToDo・習慣管理アプリは毎日・毎週のタスクを回すために作られており、「厳密な予定ではないが
間隔は気にしたい」行動には機能が過剰で、入力コストが釣り合わない。

このプロダクトは、**予定を管理しない**ことで軽さを得る。項目を並べ、やった日に 1 タップ押す。
アプリを開けば経過日数が並ぶ。それ以上のことをしない。

### 目的

- 生活行動の最終実施日を、探さずに確認できる状態をつくる
- 記録操作のコストを、継続が途切れない水準(1〜2 タップ)まで下げる
- MVP を端末内で完結させ、アカウント登録なしに初回起動から使える状態にする

## ターゲットユーザー

### プライマリーペルソナ: 佐藤ユウキ(31歳、会社員)

- スマートフォンを日常的に使い、アプリの追加・削除に抵抗がない
- タスク管理アプリを何度か試したが、入力項目の多さと通知の煩わしさで続かなかった
- 几帳面ではないが、「歯ブラシいつ替えたっけ」が気になるタイプ
- **現在の課題**: 美容院・歯医者・エアコン掃除・洗車・布団干しの最終実施日を覚えていない。
  スマホのカレンダーを遡ったりレシートを探したりして、見つからないまま諦める
- **期待する解決策**: アプリを開けば一覧が出て、やったら押すだけ。設定を求められない
- **典型的な利用**: 週に 1〜2 回、思い出したときに開く。何かを済ませた直後に開いて 1 タップ押す。
  1 回あたりの滞在は 10 秒以内

### セカンダリーペルソナ: 中村アヤ(24歳、学生)

- 消耗品(コンタクト、歯ブラシ、シャンプー詰め替え)の交換時期を管理したい
- 通知は欲しいが、鳴りすぎるアプリはすぐ消す
- **期待する解決策**: P1 の「目安期間」と控えめな通知

## 成功指標(KPI)

### プライマリーKPI

| 指標 | 目標値 | 期限 |
| --- | --- | --- |
| 1 ユーザーあたり平均登録項目数 | 5 件以上 | MVP リリース後 1 ヶ月 |
| 初回利用時に 3 件以上登録するユーザーの割合 | 50% 以上 | MVP リリース後 1 ヶ月 |
| 7 日後継続率 | 30% 以上 | MVP リリース後 1 ヶ月 |

### セカンダリーKPI

| 指標 | 目標値 | 期限 |
| --- | --- | --- |
| 初回起動時の項目登録率(1 件以上登録して離脱しない) | 70% 以上 | MVP リリース後 1 ヶ月 |
| 30 日後継続率 | 15% 以上 | MVP リリース後 2 ヶ月 |
| 1 ユーザーあたり週次の「やった」タップ回数 | 1.5 回以上 | MVP リリース後 1 ヶ月 |

**計測の前提**: MVP はユーザーデータを外部へ送信しない(非機能要件「プライバシー」)。
したがって**これらの KPI は MVP では自動計測しない**。ストアの分析指標と、リリース後に
ユーザー同意を前提とした匿名計測を別途導入した段階で測る。MVP 段階では目標値を
「設計判断の基準」として使う(例: 初回登録率 70% を狙うなら、空状態から新規登録へ
最短で到達できる導線が要る。テンプレート項目 F17 は P2 で、前倒しの判断材料になる)。

### コア機能(MVP)

#### F1. 管理項目の一覧表示

**ユーザーストーリー**:
ユーザーとして、登録した生活行動の経過日数をまとめて見たいので、起動直後に一覧が出てほしい。

**受け入れ条件**:
- [ ] アプリ起動後、他の画面を経由せず一覧画面が表示される
- [ ] 各行に「項目名」「経過日数」「最終実施日」「やったボタン」が表示される
- [ ] 経過日数が行内で最も大きく表示される(UI ガイドライン §7 の翻訳表に従う)
- [ ] 項目が 0 件のとき、空状態と新規登録への導線が表示される
- [ ] 項目が 100 件でもスクロールが引っかからない

**優先度**: P0(必須)

#### F2. 管理項目の新規登録

**ユーザーストーリー**:
ユーザーとして、気になった行動をすぐ管理対象にしたいので、項目名だけで追加できてほしい。

**受け入れ条件**:
- [ ] 一覧画面から 1 タップで登録画面/入力欄に到達できる
- [ ] 項目名のみの入力で登録が完了する(他の入力を必須にしない)
- [ ] 項目名が空、または空白のみの場合は登録できず、理由が表示される
- [ ] 項目名は 1〜50 文字。入力欄が 50 文字で打ち切る(`maxLength`)
- [ ] **保存時にも同じ検証を行う**(ペースト・IME 確定で超過しうるため)。
      超過していれば保存せず「50文字以内で入力してください」を出す
- [ ] 登録直後の項目は「未実施」状態として一覧に並ぶ(経過日数は表示しない)
- [ ] 登録開始から完了まで 30 秒以内に行える

**優先度**: P0(必須)

#### F3. 最終実施日の記録

**ユーザーストーリー**:
ユーザーとして、行動した直後に面倒なく記録したいので、ボタン 1 つで今日の日付が入ってほしい。

**受け入れ条件**:
- [ ] 一覧の各行に「やった」ボタンがある
- [ ] ボタンを押すと、その時点の日時が最終実施日として保存される
- [ ] 確認ダイアログを挟まない
- [ ] 押した直後に、その行の経過日数が「今日」に更新される
- [ ] 押したことが視覚的にフィードバックされる
- [ ] 誤タップを取り消せる(直後に取り消し導線が **4 秒間**表示される。`SnackBar` の既定)
- [ ] 取り消せるのは**直近の 1 件のみ**。別の項目を記録すると前の導線は消える
- [ ] ボタンのタッチターゲットは 56dp 以上

**優先度**: P0(必須)

> **設計判断**: アイデアメモの「まだ決めてないこと」にあった「確認ダイアログを出すか」は
> **出さない**で確定する。1 タップという中心的な価値と正面から衝突するため。
> 誤操作は確認ではなく**取り消し**で救う。

#### F4. 最終実施日の表示

**ユーザーストーリー**:
ユーザーとして、正確な日付も知りたいので、経過日数の近くに実施日が出てほしい。

**受け入れ条件**:
- [ ] 各行に最終実施日が `2026年9月12日` 形式で表示される
- [ ] 経過日数より小さく、補助情報として表示される
- [ ] 一度も記録がない項目には日付を出さず、未実施であることが分かる表示になる

**優先度**: P0(必須)

#### F5. 経過日数の表示

**ユーザーストーリー**:
ユーザーとして、判断に使うのは日付ではなく間隔なので、「何日前」を大きく見せてほしい。

**受け入れ条件**:
- [ ] 現在日と最終実施日の**暦日の差**から経過日数を算出する(経過時間ではない)
- [ ] `3日前` `42日前` `128日前` の形式で表示される
- [ ] 当日に記録した項目は `今日` と表示される
- [ ] 前日は `昨日` と表示される
- [ ] 日付をまたいだ後にアプリを開くと、経過日数が更新されている。
      **バックグラウンドからの復帰も「開く」に含む**(コールドスタートだけではない)
- [ ] 端末のタイムゾーンに従って算出する

**優先度**: P0(必須)

> **設計判断**: 経過日数は**暦日の差**で数える。「24 時間単位」だと、朝 9 時に記録して
> 翌朝 8 時に開いたとき `0日前` になり、ユーザーの「昨日やった」という認識とずれる。

#### F6. 管理項目の編集

**ユーザーストーリー**:
ユーザーとして、項目名を後から直したいので、編集できてほしい。

**受け入れ条件**:
- [ ] 一覧から各項目の編集画面に到達できる
- [ ] 項目名を変更して保存できる
- [ ] 保存すると一覧に反映される
- [ ] 最終実施日は編集操作で変化しない
- [ ] 登録時と同じ入力バリデーション(1〜50 文字、空不可)が働く

**優先度**: P0(必須)

#### F7. 管理項目の削除

**ユーザーストーリー**:
ユーザーとして、管理しなくなった項目を消したいので、削除できてほしい。

**受け入れ条件**:
- [ ] **編集画面から**項目を削除できる
- [ ] 削除は確認を挟む(記録の消失は取り返しがつかないため)
- [ ] 削除した項目は一覧から消える
- [ ] 削除しても他の項目のデータに影響しない

> **設計判断**: F3 の「やった」は確認なし、F7 の削除は確認あり。基準は
> **元に戻せるか**。記録は取り消せるが、削除は蓄積した履歴ごと失われる。
> アイデアメモの「削除データを復元できるようにするか」は MVP では**しない**(スコープ外)。

> **設計判断: 削除の入口は編集画面だけにする(一覧にスワイプ削除を置かない)。**
> 一覧上の破壊的操作は「やった」ボタンと指の動線が重なり、取り返しのつかない誤操作の
> 確率を上げる。画面遷移図(`functional-design.md`)もこの 1 経路だけを持つ。

**優先度**: P0(必須)

#### F8. データの端末内保存

**ユーザーストーリー**:
ユーザーとして、記録が消えたら意味がないので、アプリを閉じても残っていてほしい。

**受け入れ条件**:
- [ ] アプリを終了・再起動してもすべての項目と記録が残っている
- [ ] 端末を再起動してもデータが残っている
- [ ] ネットワーク接続なしですべての P0 機能が動作する
- [ ] アカウント登録・ログインを要求しない
- [ ] 保存処理の失敗がユーザーに伝わる(黙って失敗しない)

**優先度**: P0(必須)

### 将来的な機能(Post-MVP)

#### P1 機能

| ID | 機能 | 概要 |
| --- | --- | --- |
| F9 | 目安期間の設定 | 項目ごとに推奨間隔(日数)を設定する。例: 歯ブラシ 30 日、美容院 60 日 |
| F10 | 経過日数による状態表示 | 目安期間に対する経過度合いを「余裕あり / そろそろ / 経過」で示す。**色だけに頼らずラベルかアイコンを併用する** |
| F11 | 通知機能 | 目安期間を超えたときに通知する。F9 が前提 |
| F12 | 過去履歴の保存 | 最終実施日だけでなく、実施した日をすべて履歴として残す |
| F13 | カテゴリ機能 | 初期値は 生活 / 健康 / 趣味 / その他。ユーザーが追加・名前変更・削除できる。一覧上部のチップで絞り込む |
| F14 | アイコン設定 | 項目ごとにアイコンを選ぶ |
| F15 | 並び替え | 経過日数順 / 名前順 / 登録順 / 既定の並びは F30 |
| F16 | 最終実施日の手動修正 | 過去の日付に変更する。記録忘れの後追い入力に使う |
| F27 | 基準間隔の学習 | 実施履歴(F12)から項目ごとの基準間隔(直近最大 5 間隔の中央値)を学習する。ユーザーに設定を求めない。F9(目安期間の手動設定)の代替経路で、F10 の状態表示は基準間隔を使う形(#21)で実現する |
| F28 | 相対経過度による経年変化 | 相対経過度(経過日数 ÷ 基準間隔)で一覧のカードが 5 段階に古びる。基準間隔が無い項目は古びない。**色だけでなくシミ・縁の傷み・欠けの形状でも示す**。F10 を設定なしで実現する形 |
| F29 | 詳細シート | カードをタップすると「最後：14日前」「前回：7日間隔」「そろそろかも。」を最大 3 行で示す。履歴一覧・統計・基準間隔は出さない(F23 とは別物)。編集画面への入口を兼ねる。削除の入口は置かない(F7) |
| F30 | 既定の並び(相対経過度順) | 一覧の既定の並びを相対経過度の降順にする。相対経過度が無い項目は下部に登録順でまとめる。**記録操作では並びを組み替えない**(開き直し・復帰で反映)。F15 の選択 UI は持たず、既定の並びだけを変える |

**優先度**: P1(重要)

> **設計判断**: アイデアメモの「通知を MVP に含めるか」は **P1 に置く**。通知は目安期間(F9)
> が前提で、F9 は「設定を求めない」という MVP の中心方針と逆を向く。両方まとめて P1 に送る。
> **ただし F12(履歴)はデータモデルに影響する**ため、MVP のスキーマ設計時点で拡張余地を残す
> (技術仕様で扱う)。

#### P2 機能

| ID | 機能 | 概要 |
| --- | --- | --- |
| F17 | テンプレート項目 | 歯ブラシ・美容院・エアコン掃除・歯医者・洗車・布団干しをワンタップ追加 |
| F18 | ホーム画面ウィジェット | 経過日数の長い項目を数件表示する |
| F19 | クラウド同期 / 複数端末同期 | バックエンドとアカウントが前提 |
| F20 | 家族との項目共有 | F19 が前提 |
| F21 | 項目ごとのメモ | |
| F22 | 写真記録 | 掃除前後・交換した商品など |
| F23 | 統計表示 | 平均実施間隔・年間実施回数。F12 が前提 |
| F24 | ゲーミフィケーション | 経験値・バッジ・成長要素 |
| F25 | テーマ・カラーカスタマイズ | |
| F26 | データのバックアップ / エクスポート | 端末機種変更時の移行手段 |

**優先度**: P2(できれば)

> **F17(テンプレート項目)は P2 に置いたが、KPI「初回 3 件以上登録 50%」に最も効く機能**でもある。
> MVP リリース後に初回登録率が目標を下回った場合、**最初に前倒しを検討する候補**とする。

## 非機能要件

### パフォーマンス

| 要件 | 基準 |
| --- | --- |
| 起動から一覧表示まで | コールドスタートで 1.5 秒以内(ミドルレンジ端末) |
| 「やった」タップから画面反映まで | 100ms 以内 |
| 項目数 100 件でのスクロール | フレーム落ちなし(60fps 維持) |
| 項目数 100 件での一覧初回描画 | 300ms 以内 |

### ユーザビリティ

| 要件 | 基準 |
| --- | --- |
| 初回利用 | 説明・チュートリアルなしで項目登録と記録ができる |
| 項目登録 | 開始から完了まで 30 秒以内 |
| 最終実施日の確認 | アプリ起動から 5 秒以内 |
| 記録操作 | 1〜2 タップ以内で完了する |
| 片手操作 | 主要な操作(やったボタン・項目追加)が片手の親指の可動域に収まる |

### 信頼性

| 要件 | 基準 |
| --- | --- |
| データ永続性 | アプリ再起動・端末再起動でデータが消えない |
| 保存失敗の可視化 | 書き込みに失敗した場合、成功したかのように見せない |
| 誤操作からの回復 | 「やった」の誤タップを取り消せる |
| クラッシュ | 一覧・登録・記録の主要導線でクラッシュしない |

### セキュリティ / プライバシー

| 要件 | 基準 |
| --- | --- |
| データの所在 | MVP では**アプリが能動的に**ユーザーデータを外部サーバーへ送信しない(下記の注記を参照) |
| 認証 | MVP では実装しない。アカウント登録を求めない |
| 権限 | 端末の権限要求は最小限(MVP では通知権限も要求しない) |
| 収集する情報 | MVP では行動ログ・解析データを収集しない |

> **OS 標準バックアップは例外として許容する。** iCloud バックアップ / Android Auto Backup に
> DB ファイルが含まれるため、**クラウド上にデータのコピーは存在する**。MVP に手動エクスポート
> (F26)が無い以上これが唯一の機種変更手段であり、意図的に除外指定しない
> (`architecture.md`「バックアップ戦略」)。上の「送信しない」は**アプリ自身が通信しない**
> ことを指す。**プライバシーポリシーとストアのデータ収集申告に明記する。**

### オフライン対応

| 要件 | 基準 |
| --- | --- |
| 機能の可用性 | インターネット接続なしで P0 機能がすべて動作する |
| 接続前提の表示 | オフラインを理由にしたエラー表示・機能制限を出さない |

### アクセシビリティ

| 要件 | 基準 |

## スコープ外

MVP で明示的に作らないもの:

- アカウント登録・ログイン・認証
- バックエンド API・クラウド同期・複数端末対応
- 通知、および通知のための目安期間設定(P1 に送る)
- 過去履歴の保持(最終実施日のみを持つ。ただしスキーマは拡張可能にする)
- 最終実施日の手動修正(P1)
- カテゴリ・アイコン・並び替え(P1)
- 削除データの復元・ゴミ箱
- データのエクスポート・バックアップ
- ホーム画面ウィジェット
- 収益化(広告・課金・登録件数制限)。無料・広告なしで出す
- 多言語対応
- タブレット / 横向きレイアウトの最適化
- ダークモードの独自設計(Material 3 のシードから自動生成されるものは動くが、個別調整はしない)

## 未決事項

MVP の実装開始までに決める必要はないが、リリース前に判断が要るもの:

| # | 論点 | 判断の期限 |
| --- | --- | --- |
| 1 | 収益化方法(無料 / 広告 / 買い切り / サブスク) | 正式リリース前。MVP は無料・広告なし |
| 2 | iOS / Android を同時リリースするか | ストア申請の準備時 |
| 3 | ストア掲載名(「最後にいつ」か LastWhen か) | ストア申請の準備時 |
| 4 | 匿名利用統計の導入可否(KPI 計測のため) | MVP リリース後、初回の効果測定時 |
| 5 | プライバシーポリシーの内容と掲載先(OS バックアップ経由のデータ所在を含む) | **ストア申請の準備前**。Apple / Google とも**掲載 URL が申請の必須項目**で、無いと申請できない |
| 6 | iOS ビルド用の macOS + Xcode 環境をどう確保するか(実機 / CI / 借用) | **ストア申請の準備前**。#2(iOS を出すか)と連動する。現状は「制約として残っている」だけで担当も期限も無い |
